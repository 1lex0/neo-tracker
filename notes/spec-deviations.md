# Отклонения и неясности спецификации

Журнал мест, где спецификация (`specs/001-nasa-neo-tracker/`) была неясной,
противоречивой или неполной, и решений, принятых агентом реализации.
Формат: **что в спецификации → что сделано → почему**.

## Фаза 1: Setup

### D1. Тестовый проект ссылается не только на Core, но и на Api

- **Спецификация**: T001 — «reference Core from Api and UnitTests», то есть тесты
  ссылаются только на `NeoTracker.Core`.
- **Противоречие**: T021 (`NasaNeoClientTests`) и T023 (`JsonDailyResultCacheTests`)
  требуют тестировать `NasaNeoClient` и `JsonDailyResultCache`, которые по T007/T014
  лежат в `src/NeoTracker.Api/`. Без ссылки на Api эти тесты невозможны.
- **Сделано**: `NeoTracker.UnitTests` ссылается на `NeoTracker.Core` и `NeoTracker.Api`.
- **Почему**: иначе пришлось бы переносить клиент и кэш в Core, что противоречит
  структуре из plan.md. Ссылка на Api — минимальное изменение.

### D2. Фиксированный порт API и только HTTP

- **Спецификация**: T002 требует проксировать `/api` «to the local ASP.NET Core API»,
  но порт API нигде не задан.
- **Сделано**: профиль `http` в `launchSettings.json` слушает `http://localhost:5080`;
  HTTPS-профиль и `UseHttpsRedirection` из шаблона убраны. Прокси Vite по умолчанию
  указывает на этот адрес (переопределяется переменной `NEO_API_URL`).
- **Почему**: шаблон генерирует случайный порт; HTTPS-редирект при проксировании
  с `http://localhost` через Vite только мешает локальной разработке.

## Фаза 2: Foundational

### D3. Тип-исход `DailyResultOutcome` и `NasaUnavailableException` сверх списка T004/T005

- **Спецификация**: T004 перечисляет модели (`SelectedDate`, `AsteroidObservation`,
  `DailyResult`, `CachedDailyResult`, `ApiResponse`, `ApiError`), T005 — три интерфейса.
  Как сервис сообщает эндпоинту, какое из пяти «Display State» (data-model.md) выбрано,
  не описано.
- **Сделано**: добавлен `Core/Models/DailyResultOutcome.cs` (Fresh, NoResultsFallback,
  NoResultsNoCache, UpstreamFailure, InvalidDate) и исключение
  `NasaUnavailableException` в `INasaNeoClient.cs`.
- **Почему**: решение о состоянии — бизнес-логика и должно жить в Core и
  тестироваться (FR-013); эндпоинт только переводит исход в HTTP-ответ.

### D4. Ключ NASA берётся только из `NASA_API_KEY`, не из секции `Nasa`

- **Спецификация**: T006 — читать `NASA_API_KEY` из runtime-конфигурации.
- **Сделано**: `Nasa:BaseAddress` читается из appsettings, но `ApiKey` намеренно не
  биндится из `appsettings.json` — только из `NASA_API_KEY` (env, user-secrets, CLI),
  иначе `DEMO_KEY`.
- **Почему**: чтобы ключ нельзя было случайно закоммитить в `appsettings.json`
  (принцип IV конституции).

### D5. Кэш: одна запись на дату; нечитаемый файл не роняет приложение

- **Спецификация**: data-model описывает `CachedDailyResult`, но не говорит, что делать
  при повторном запросе той же даты и при повреждённом файле кэша.
- **Сделано**: кэш хранит одну (последнюю) запись на дату. Если файл кэша не читается,
  приложение стартует с пустым кэшем, а испорченный файл копируется в
  `<cache>.unreadable`, чтобы следующая запись его молча не уничтожила.
  `SaveAsync` возвращает `false` при ошибке записи (а не бросает исключение), чтобы
  свежий ответ NASA всё равно дошёл до пользователя.
- **Почему**: принцип I (не падать), принцип II (не терять данные).

### D6. Порядок задач: заготовка `NasaNeoClient` в фазе 2

- **Спецификация**: T008 (фаза 2) требует зарегистрировать typed NASA client с таймаутом
  30 с, а сам клиент реализуется в T014 (фаза 3).
- **Сделано**: в фазе 2 создан класс-заготовка `NasaNeoClient` (метод бросает
  `NotImplementedException`), чтобы регистрация компилировалась; реализация — в T014.
  Аналогично `DailyResultService` регистрируется в DI в T015, когда он появляется.
- **Почему**: иначе T008 нельзя выполнить в своей фазе.

## Фаза 3: US1 — просмотр астероидов

### D7. Язык интерфейса: «Получить данные» vs «Get Data»

- **Спецификация**: исходное описание в spec.md — кнопка «Получить данные»;
  quickstart.md — «select **Get Data**»; сообщения об ошибках в контракте — на английском.
- **Сделано**: интерфейс на русском (кнопка «Получить данные», подписи, сообщения).
  Бэкенд отдаёт английские `message` по контракту; фронтенд показывает русский текст,
  выбирая его по стабильному `code`, а `message` бэкенда — только для неизвестных кодов.
- **Почему**: формулировка пользователя первична; стабильные `code` в контракте как раз
  и предназначены для такой локализации.

### D8. Поле даты — текстовое, а не `<input type="date">`

- **Спецификация**: «пользователь вводит дату в формате ГГГГ-ММ-ДД»; при этом требуется
  показывать ошибки формата и несуществующих дат (31 февраля).
- **Сделано**: `<input type="text">` с плейсхолдером `ГГГГ-ММ-ДД`.
- **Почему**: нативный date-picker не даёт ввести неверный формат или 30.02, и
  сценарии US3 стали бы непроверяемыми.

### D9. Интерпретация ответа NASA

- **Спецификация**: «map required asteroid fields and the first relevant
  close-approach measurements»; поведение при отсутствии ключа даты и при одном
  битом объекте в массиве не описано.
- **Сделано**:
  - отсутствие ключа выбранной даты в `near_earth_objects` = пустой день (не ошибка);
  - из `close_approach_data` берётся запись с `close_approach_date` == выбранной дате,
    иначе первая;
  - числа принимаются и как JSON-number, и как строка (NASA отдаёт скорость и
    расстояние строками);
  - если хотя бы один объект не проходит валидацию (нет поля, отрицательный диаметр,
    max < min), весь ответ считается нечитаемым → upstream failure (503), а не
    «частичный успех».
- **Почему**: контракт требует считать неожиданную форму ответа сбоем, а конституция —
  валидировать данные до использования; молча выбрасывать объекты значило бы показывать
  неполные данные как полные.

### D10. Фаза 3 содержит временную проверку даты

- **Спецификация**: валидатор `SelectedDateValidator` — задача T032 (фаза 5), а эндпоинт
  из T015 (фаза 3) уже должен принимать дату.
- **Сделано**: в фазе 3 сервис использовал `DateOnly.TryParseExact`; в фазе 5 заменён
  на `SelectedDateValidator`.

## Фаза 4: US2 — кэш и отказоустойчивость

### D11. Пустой ответ не затирает непустой день той же даты

- **Спецификация**: Assumptions — «Successfully received empty results may be retained,
  but do not replace the last non-empty day eligible for display». Неясно, относится ли
  это к той же дате (кэш хранит одну запись на дату, D5).
- **Сделано**: если NASA вернул пустой список для даты, по которой в кэше уже есть
  непустой день, кэш не перезаписывается; иначе пустой день сохраняется.
  Логика — в `DailyResultService` (Core), покрыта тестом.
- **Почему**: буквальное прочтение Assumptions; иначе повторный пустой ответ мог бы
  уничтожить единственный пригодный для fallback день.

### D12. `GET /api/asteroids/cache/latest` и поле `requestedDate`

- **Спецификация**: эндпоинт возвращает «the successful result shape», где
  `requestedDate` — обязательная строка, но у самого эндпоинта нет параметра даты.
- **Сделано**: добавлен необязательный query-параметр `requestedDate`; если он передан
  и валиден — возвращается в ответе, иначе `requestedDate: null`. Фронтенд передаёт
  дату, на которой случился сбой.
- **Почему**: без даты запроса нельзя выполнить SC-006 (пользователь должен видеть, что
  показанная дата отличается от запрошенной), а делать параметр обязательным — менять
  контракт сильнее, чем нужно.

### D13. Метка времени у fallback-ответа

- **Спецификация**: для fallback не сказано, какое `receivedAtUtc` отдавать — время
  текущего (пустого) ответа или время получения кэшированного дня.
- **Сделано**: всегда время получения кэшированного дня; `source` — тоже из кэша,
  а UI добавляет пометку «(из локального кэша)» и баннер «это не свежий ответ».
- **Почему**: FR-012 — нельзя выдавать устаревшие данные за свежие; текущее время рядом
  со старыми данными вводило бы в заблуждение.

### D14. При сбое NASA предлагается последний непустой день, а не кэш запрошенной даты

- **Спецификация**: контракт фиксирует, что при 503 предлагается «latest-received cached
  non-empty day». Если в кэше есть данные именно за запрошенную дату, но получены
  раньше другого дня, будет предложен другой день.
- **Сделано**: строго по контракту — последний полученный непустой день.
- **Почему**: явно прописано в контракте и data-model; отмечаю как возможное улучшение
  (предлагать кэш запрошенной даты, если он есть).

## Фаза 5: US3 — валидация ввода

### D15. Строка из одних пробелов — «пустое поле» или «неверный формат»?

- **Спецификация**: T032 — «reject empty input, extra whitespace»; к какой категории
  отнести `"   "`, не сказано.
- **Сделано**: строка только из пробелов → `Required` (как пустая); любые пробелы рядом
  с датой (`" 2026-10-27"`) → `InvalidFormat`. Также `\z` вместо `$` в регулярке, чтобы
  `"2026-10-27\n"` не проходил (в .NET `$` допускает завершающий перевод строки).
  Год `0000` → `ImpossibleDate` (в григорианском календаре .NET года 0 нет).
- **Почему**: для пользователя пробелы — это «ничего не введено»; при этом строгий
  формат `YYYY-MM-DD` без обрезки.

### D16. Кнопка: отключена только при пустом поле

- **Спецификация**: FR-002 — кнопка неактивна, пока поле пустое; FR-004 — при неверном
  формате показать сообщение и не делать запрос.
- **Сделано**: при пустом поле кнопка `disabled` и сразу видна подсказка «обязательное
  поле»; при непустом неверном значении кнопка активна, но нажатие показывает ошибку
  формата/несуществующей даты и запрос не отправляется. После первой попытки сообщение
  обновляется по мере ввода.
- **Почему**: так выполняются и FR-002, и сценарий US3-2/3 «When the user attempts to
  retrieve data, Then the user sees a format error» — попытка должна быть возможна.

### D17. Валидация продублирована на фронтенде без unit-тестов

- **Спецификация**: T034 требует показывать сообщения в форме и не вызывать бэкенд для
  неверных дат; FR-013/конституция требуют unit-тестов для валидации; тест-раннер —
  только xUnit (`dotnet test`).
- **Сделано**: `frontend/src/validation/date.ts` повторяет правила
  `SelectedDateValidator` с русскими сообщениями. Авторитетной остаётся серверная
  проверка (покрыта xUnit, включая 400 `invalid_date` без вызова NASA). Отдельного
  JS-тест-раннера (Vitest) не добавлял.
- **Почему**: README должен описывать **одну** команду для тестов, и plan выбирает
  xUnit; второй раннер усложнил бы проект (принцип V). Это осознанный пробел: клиентская
  копия правил не покрыта автотестами — проверена вручную (см. фазу 6).
